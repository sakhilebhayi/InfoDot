## What is backed up, and what is not

One encrypted archive per app per run. The estate is found the same way `tools/apply-secrets.sh` finds it: every
`~/<hostlabel>.infodot.co.za/` docroot, and the single `artisan` under it (two levels deep at most). The host label is
mapped back to the key (`pres` to `press`, `sheets` to `sheet`, `doc` to `docs`), and `~/public_html` is used for
InfoDot when `~/infodot.infodot.co.za` does not exist. Files lives in `dotfiles`, which is found by the `artisan` search.
A docroot with more than one `artisan` is reported as AMBIGUOUS and not guessed; `~/.dot-backup/apps.list`
(`key /absolute/path` per line) settles it without changing the tool.

| Part | Backed up | How |
|---|---|---|
| SQLite database | yes | the SQLite online-backup API: `sqlite3 .backup`, else PHP `SQLite3::backup` (or `VACUUM INTO` where PHP has no `backup()`). If neither tool exists the app is **refused**; the live file is never copied with `cp`. Safe while the app writes (WAL included). |
| MySQL / MariaDB database (InfoDot, Mines) | yes | `mysqldump --single-transaction --quick`, credentials only through a temporary mode-600 defaults file that is removed afterwards. Consistent for InnoDB; MyISAM tables are not snapshot-consistent. |
| PostgreSQL database (Projects) | yes | `pg_dump` (plain SQL) with a temporary mode-600 password file in `PGPASSFILE`; no password on any command line. |
| `.env` | yes | a plain copy inside the encrypted archive (it holds `APP_KEY` and every secret, which is why the archive is encrypted). |
| User uploads: `storage/app` | yes, when the app has any file there | top-level entries of `storage/app` except `backups`, `cache`, `framework`, `logs`, `tmp`; capped at `DOT_BACKUP_UPLOADS_MAX_MB` (default 200). Over the cap the uploads are skipped, the app is still backed up, and the manifest line and the inventory carry `uploads_over_cap`. |
| Application code, `vendor`, `node_modules` | no | they come from git and the deploy pipeline. |
| `storage/logs`, `storage/framework` (cache, sessions files, views), `storage/backups` | no | rebuildable or already covered. `storage/backups` is where Dopemine's and Central's own nightly SQLite command writes (see below). |
| Files an app keeps outside `storage/app` (for example under `public/`) | **no, and not detected** | which apps do this is unknown until someone looks; the inventory only sees `storage/app`. |
| The crontab, `~/.dot-cron.d`, cPanel settings, DNS, mail, MySQL users and grants | no | outside the apps. The cron command files are regenerated by each app's deploy pipeline. |
| Non-Laravel parts of the host (no `artisan`) | no | the inventory lists docroots without an app so this is visible. |

### Coexistence with the per-app SQLite commands (Dopemine, Central)

Those two apps already write their own nightly online backup into `storage/backups`. They are left alone. The host
tool also backs up their databases (through the same online-backup API) into `~/dot-backups/<key>/`, encrypted, with
the same retention as every other app. The two sets are independent: neither reads or deletes the other. The per-app
copies stay unencrypted inside the app folder and are only as safe as the app folder.

## Where, in what form

```
~/dot-backups/                      mode 700
  manifest.log                      one plain line per app per run: no content, no secrets
  cron.log, offsite.log             output of the nightly job / of the off-host hook
  <key>/                            mode 700
    <key>-YYYYmmdd-HHMMSS.tar.gz.enc        mode 600, UTC time in the name
    <key>-YYYYmmdd-HHMMSS.tar.gz.enc.sha256 mode 600, "<hex>  <file name>" of the ciphertext
  .stage/  .restore-test/           scratch; emptied at the start of each run / removed by verify and restore-test
~/.dot-backup/                      mode 700
  passphrase                        mode 600, 48 random bytes in base64; the tool refuses to run if it is missing or not 600
  offsite.sh                        optional hook, see below
  apps.list                         optional overrides
```

A manifest line looks like this (counts only):

```
2026-10-22T02:40:11Z key=tasks driver=sqlite db_bytes=1048576 archive_bytes=212345 seconds=3 status=ok
2026-10-22T02:40:20Z key=mines driver=mysql db_bytes=0 archive_bytes=0 seconds=2 status=failed reason=mysqldump_failed
```

The archive (`tar`, then `gzip`, then `openssl enc`) holds: `meta.txt` (key, driver, UTC time, source folder, what the
database file is called, whether uploads are included), `database.sqlite` or `database.sql` (or nothing for an app with
no database, flagged `no_database`), `env`, and `uploads.tar` when there are uploads.

## Encryption and key handling

* Cipher: `openssl enc -aes-256-cbc -pbkdf2 -iter 200000 -md sha256` with a random salt, key derived from the
  passphrase file. Passphrase: `openssl rand -base64 48`, written by `dot-backup init` with mode 600, **never printed**
  by the tool or by the workflow.
* What this protects: a copy of the archives (stolen disk, a leaked off-host bucket) is unreadable without the
  passphrase. What it does not protect: anyone who already has a shell as the hosting user can read the passphrase file,
  the `.env` files and the live databases anyway. AES-CBC is not authenticated: the `.sha256` file catches accidental
  corruption and a truncated copy, it does not stop someone who can rewrite both files. (Verified in the fake-host
  test: no SQLite header, no `APP_KEY` and no secret appears in any archive; the files start with `Salted__`.)
* **The passphrase must also be kept off the host.** Without it every archive is unrecoverable, and the host copy
  disappears together with the host. Read it once, in your own terminal, and paste it into your password manager:

  ```
  ssh <user>@<host> 'cat ~/.dot-backup/passphrase'
  ```

  Do not read it through a GitHub workflow (the job log would keep it). Then clear the terminal scrollback. Check the
  stored copy by restoring with it from another machine (`DOT_BACKUP_PASSFILE=/path/to/copy dot-backup restore ...`,
  the copy must be mode 600).
* If the host copy is lost and the off-host copy exists: put the copy back at `~/.dot-backup/passphrase` (mode 600).
  If **both** are lost, the archives cannot be opened by anyone; run `init` for a new passphrase and take new backups.
* Rotation: move the old file aside, run `init` (it creates a new one), run a backup, and keep the **old** passphrase
  in the password manager until the last archive made with it has aged out of retention (at most six months). New
  archives use the new passphrase; old ones still need the old one (`DOT_BACKUP_PASSFILE`).

## Schedule and retention

* **Cadence (planned, set by the `schedule` mode):** nightly at 02:40 host time, `flock -n`, output appended to
  `~/dot-backups/cron.log`. The line is added through the same safe block the deploy pipelines use for the shared
  crontab (one writer on `~/.dot-crontab.lock`, a read trusted only when non-empty or "no crontab", a timestamped backup
  `~/.dot-crontab.backup-*`, a read-back check, the previous crontab restored on any difference). Only the line marked
  `# dot-backup` is ever touched; `unschedule` removes it. The cron environment is minimal, so the line carries the
  `PATH` of the session that scheduled it (paths only).
* **Resource use (design, not measured on the host):** one app at a time (`DOT_BACKUP_PARALLEL=1`), `nice -n 19` and
  `ionice -c3` where present, a per-app `timeout` (900 s), a streaming `tar | gzip | openssl` pipeline, the database
  copy staged on disk first (so a run needs about twice the database size free; the tool refuses an app when `df`
  says there is not enough). The account limits it works inside: 1 GB RAM, 100 processes, 30 entry processes
  (R-1); disk 29.3 GB with 12.34 GB used at the R-1 reading.
* **Retention (applied after each successful app; `prune` applies it on demand):** the newest 14 archives of an app
  plus the first archive of each of the last 6 calendar months (the current month included). Both numbers are
  environment settings (`DOT_BACKUP_KEEP`, `DOT_BACKUP_KEEP_MONTHS`). At most about 20 archives per app. The disk this
  needs has **not** been measured: after the first `run`, `du -sh ~/dot-backups` and the manifest give the real number.
* Two runs never overlap (`flock` on `~/dot-backups/.lock`; the second exits 75 and says so). One failing app does not
  stop the others; the run exits non-zero if any app failed.

## Operating it

From GitHub Actions: workflow **Backups** (fixed modes, SSH secrets `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`,
`DEPLOY_KNOWN_HOSTS`):

| Mode | What it does |
|---|---|
| `install` | syntax-checks the tool, copies it to `~/bin/dot-backup`, compares checksums, runs `--help` and `init` |
| `inventory` | read-only list: key, folder, driver, database size, `.env`, uploads size, newest backup and its age; flags NO-BACKUP, STALE(>36h), NO-DB, NO-ENV, AMBIGUOUS, a missing dump tool |
| `run` (keys optional) | back up all apps or the named ones, with per-step timings |
| `verify` (keys optional) | decrypt the newest archive of each app into scratch; check sha256, `tar -t`, SQLite `PRAGMA integrity_check` and table/row counts, the footer of a MySQL/PostgreSQL dump; print counts only; remove the scratch |
| `restore-test` (one key optional) | restore the largest newest archive (or the named key) into `~/dot-backups/.restore-test/`, print timings and the integrity result, remove it |
| `schedule` / `unschedule` | add / remove the one nightly cron line |

On the host the same things are `dot-backup init | inventory [--strict] | run [key ...] | verify [key ...] |
restore <key> <archive> <dir> | restore-test [key] | prune [key ...] | schedule | unschedule`, with `--time` for step
timings. `.env` values are parsed, never sourced, and used only to reach the database; no mode prints file contents,
passwords or the passphrase. Failure reasons are fixed words (`mysqldump_failed`, `no_sqlite_tool`, `low_disk_space`,
`sqlite_file_missing`, `unsupported_driver`, `ambiguous_app_folder`, `timeout_or_crash` and a few more); a tool's own
first error line is shown with the app's database password replaced by `***`.

## Restore, step by step

Nothing in the tool restores into a live app. `restore` and `restore-test` write only into a **new, empty directory**
and refuse any target that is, contains or lies inside an app folder, a docroot, `~/public_html` or the home
directory, or inside `~/dot-backups` outside `.restore-test/`. They never overwrite a database. (Verified in the
fake-host test with eight refused targets.)

### A. Look at a backup (safe, any time)

1. `dot-backup inventory` to see the newest archive of the app, or `ls -l ~/dot-backups/<key>/`.
2. `dot-backup --time restore <key> ~/dot-backups/<key>/<key>-YYYYmmdd-HHMMSS.tar.gz.enc ~/restore-check/<key>`
   (the parent `~/restore-check` must exist; the target must not).
3. It prints the restored file names and sizes and the check result (`integrity=ok tables=N rows=M`, or the dump
   footer check). Open the data with `sqlite3`, `mysql` or `psql` as usual, then `rm -rf ~/restore-check/<key>`.

### B. Real restore into a live app (manual; the tool does not do this)

Decide first what is lost: a damaged database, a deleted table, an overwritten `.env`, lost uploads. Restore only that
part. Use a scratch restore (A) to confirm the archive holds what you expect before touching anything.

1. **Stop the writers.** `php artisan down` in the app folder. The cron runner and queue workers keep starting
   `artisan` processes: move the app's command file away for the duration, `mv ~/.dot-cron.d/<key>.cron
   ~/.dot-cron.d/<key>.cron.paused` (put it back at the end; the app's next deploy would also rewrite it).
2. **Keep what is there.** SQLite: copy the live `database.sqlite` and any `-wal`/`-shm` files next to it
   (`cp -p`), now safe because writers are stopped. MySQL/PostgreSQL: take a fresh dump first (`dot-backup run <key>`).
3. **Put the data back.**
   * SQLite: restore with step A into a scratch directory, then replace the live file with the restored
     `database.sqlite` (`mv` the old one aside, copy the restored one in, same owner and mode, **remove any stale
     `database.sqlite-wal` and `-shm`** of the old file).
   * MySQL: load `database.sql` into a scratch database first (`mysql --defaults-extra-file=<mode 600 file> -e 'CREATE
     DATABASE restore_check'`, then import), check it, then import into the real database (drop or empty the damaged
     tables first). Never put the password on the command line.
   * PostgreSQL: same with `psql` and a `PGPASSFILE`.
   * Uploads: `uploads.tar` holds paths relative to `storage/app`; extract it into a scratch directory and copy back
     only the missing files (`tar -xf uploads.tar -C <scratch>`), not over newer ones.
   * `.env`: compare the restored `env` with the live one (`diff`) and copy over only the lines you need; an old
     `.env` can silently revert newer secrets.
4. `php artisan config:clear` if the app caches config, then `php artisan up`. Check `/up` and a page that reads the
   restored data. Put the `.cron` file back.
5. `dot-backup run <key>` straight away so there is a fresh archive of the restored state, and write the incident,
   the time it took and what was lost into `EXECUTION_LOG.md`.

The manual swap time (steps 1 to 5) is the second term of the RTO below; it has not been measured and is not estimated
here.

## Off-host copy: the pluggable hook

The tool never needs network access. After a `run` in which at least one app was backed up, if
`~/.dot-backup/offsite.sh` exists and is **executable**, it is called once with the paths of the new `.enc` archives as
arguments (the matching checksum is `<path>.sha256`; `manifest.log` is in `$DOT_BACKUP_ROOT`):

* environment: `DOT_BACKUP_ROOT` (the backup directory), `DOT_BACKUP_COUNT` (number of archives);
* run under `timeout` (`DOT_BACKUP_OFFSITE_TIMEOUT`, default 1800 s); its output goes to `~/dot-backups/offsite.log`
  (never to the job log, so a careless hook cannot leak into GitHub);
* refused if it is writable by group or others; skipped with a message if not executable;
* a failure is **reported, not fatal**: the run prints `off-host: hook FAILED rc=N`, appends an `offsite status=failed`
  line to `manifest.log`, still exits 0 when every app was backed up, and `inventory` shows the last hook result;
* the archives are already encrypted, so the hook never needs the passphrase. Keep its own credentials in a mode-600
  config file, not in the script.

Whether the shared host may open outbound S3 or SFTP connections is **not verified**. The pull alternative needs no
hook at all: from the owner's machine, `rsync -e ssh <user>@<host>:dot-backups/ <local dir>` (read-only use of the same
SSH access). Examples, documentation only, nothing here has been run:

```sh
#!/bin/sh
# ~/.dot-backup/offsite.sh -- S3-compatible bucket with the AWS CLI (credentials in ~/.aws/credentials, mode 600)
set -eu
BUCKET="s3://EXAMPLE-BUCKET/dot-backups"; ENDPOINT="https://s3.EXAMPLE.invalid"
for f in "$@"; do
  key="$(basename "$(dirname "$f")")"
  aws s3 cp --only-show-errors --endpoint-url "$ENDPOINT" "$f" "$BUCKET/$key/"
  aws s3 cp --only-show-errors --endpoint-url "$ENDPOINT" "$f.sha256" "$BUCKET/$key/"
done
# with rclone instead (remote "offsite" defined in ~/.config/rclone/rclone.conf, mode 600):
#   rclone copyto "$f" "offsite:EXAMPLE-BUCKET/dot-backups/$key/$(basename "$f")"
```

```sh
#!/bin/sh
# ~/.dot-backup/offsite.sh -- SFTP with key authentication (a key used only for this)
set -eu
DEST="backup@EXAMPLE-HOST"; DIR="dot-backups"
for f in "$@"; do
  key="$(basename "$(dirname "$f")")"
  printf -- '-mkdir %s\n-mkdir %s/%s\nput %s %s/%s/\nput %s.sha256 %s/%s/\n' \
    "$DIR" "$DIR" "$key" "$f" "$DIR" "$key" "$f" "$DIR" "$key" |
    sftp -i "$HOME/.ssh/offsite_key" -o BatchMode=yes -o StrictHostKeyChecking=yes -b - "$DEST"
done
```

Whatever receives the copies needs its own retention and its own access control; the on-host retention does not
reach it.

## RPO and RTO

* **RPO** (how much data can be lost) = the time since the last successful backup of that app. At a nightly cadence the
  worst case is 24 h plus the time the run takes; it is shorter right after a run. The `inventory` age column is the
  live value. Anything older than 36 h is flagged. Off-host, the RPO is the age of the last copy that left the host.
* **RTO** (how long until the app is back) = measured restore seconds (`restore-test`: sha256 check, decrypt,
  extract, integrity check) + the manual swap of section B. The restore term is measured by the Backups workflow in
  `restore-test` mode, which prints `restore_seconds`, `archive_bytes` and `extracted_kb`; the swap term is
  timed by the owner on the first real or rehearsed swap. It scales with archive size, so the largest archive is the
  cautious sample, and a whole-estate restore is not the sum of one app's number.

## Known limits and risks

* Never run on the host. Everything above is verified only against the fake host in `tools/test-backup-host.sh`
  (stubbed `mysqldump`/`pg_dump`/`crontab`); real clients, real versions, real permissions and real sizes are untested.
* A backup on the same account protects against a bad deploy, a deleted row or a corrupted file, not against losing
  the account or the host. That needs the off-host copy.
* The nightly run adds load to a host that already hit its process and memory limits (R-1). It runs at low priority,
  one app at a time, and a dispatch from GitHub keeps one SSH session open for its whole duration (the host has dropped
  SSH sessions before); a dropped session stops the run, leaves no partial archive, and the next run cleans the staging
  area.
* `.env` values using `${OTHER}` interpolation are not expanded when the tool reads the database settings.
* Uploads outside `storage/app` are not covered (see the table above).
