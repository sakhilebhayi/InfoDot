# R-24 — Owner brief (2026-10-31), stored verbatim (formatting condensed, content complete)

# INFODOT — FINAL PRODUCTION READINESS, BUSINESS VALIDATION & MARKET LAUNCH EXECUTION

## Mission: Move InfoDot from a technically mature platform to a functioning business that serves real entrepreneurs.

Address the remaining weaknesses and move the platform towards its actual purpose: helping people start businesses, solve business problems, improve operations and grow successful companies. The current assessment suggests a strong technical foundation without real market adoption, a validated revenue model, or several operational requirements. Confront this honestly and execute. **The objective is no longer simply to build a better platform. The objective is to make InfoDot operationally reliable, commercially functional, publicly accessible and useful to real businesses.** Do not rebuild implemented and verified features; do not repeat completed work for another impressive audit. Identify what is genuinely outstanding, validate it and close it.

## 1. Establish the actual state
Final evidence-based assessment of production, repositories, infrastructure and programme documentation (start from R-17, R-10 and the programme records). Treat reported achievements (≈1,350 tests, 11 CI gates, enforced nonce CSP with zero violations, headers, hardened sessions, OIDC provider, closed satellite registration, encrypted nightly backups + restore tooling, daily ops checks, deploy pipeline with rollback, rich-media Q&A, tried-it, mentions, versioning, duplicate detection, seminars/tiers/licensing, 20-entry sourced library) as claims to verify against implementation, production configuration, CI results, deployment evidence and operational records. Produce a concise status register: implemented / deployed / verified in production / incomplete / never tested with real users or transactions / requires owner / requires provider or registrar. Do not modify functioning systems unnecessarily.

## 2. Critical operational priorities (before public launch)
**Priority 1 — Domain** (reported expiry 27 Nov 2026; highest operational risk): establish registration status, actual expiry, registrar and renewal requirements, auto-renew, payment status, DNS continuity, other ecosystem use. Prepare exact renewal instructions and the owner action; complete permitted steps only if registrar access is available and explicitly authorised. Verify through registrar confirmation and updated expiry. Acceptance: a confirmed renewal extending beyond the current expiry, with evidence — prepared instructions do not count as renewed.
**Priority 2 — MySQL restore drill**: nightly backups are not proven until a real restore succeeds. Controlled drill in an isolated environment: latest encrypted backup; access + decrypt via the authorised process; restore to an isolated DB; schema integrity; record counts and relationships; critical application queries; essential functionality against the restored DB; restoration duration; data-loss window vs intended RPO; recovery duration vs intended RTO; document and correct failures. Never overwrite live production. Acceptance: a successful, documented restore with integrity checks and measured recovery results.
**Priority 3 — Live Paystack validation**: first inspect Dot.Billing — deployed? operational? correctly integrated with InfoDot? Investigate production deployment status, pipeline, environment configuration, production credentials, webhook configuration, subscription/tier integration, payment records and reconciliation, error handling and logging. Then a controlled live payment test with explicit owner approval: success, failure, cancelled checkout, webhook delivery + signature validation, duplicate delivery/idempotency, subscription activation, renewal/lifecycle, receipts, failure handling. Verify server-side against Paystack records (a browser redirect is not evidence). Approved test amount and account; no unintended charges. If Dot.Billing is not deployed, resolve deployment and integration blockers first. Acceptance: at least one real authorised transaction confirmed by Paystack and correctly reflected in Dot.Billing and InfoDot.
**Priority 4 — DNS and email security** (per the R-18 register): DMARC rua, enforcement progression (identify all legitimate senders; aggregate reporting; analyse; fix SPF/DKIM alignment; p=none → quarantine → reject only after validation); CAA with approved CAs without breaking issuance; DNSSEC via the supported registrar/provider process with external chain verification; OpenSSH configuration review; disable FTP or move to SFTP; provider confirmation where changes cannot be made from the application environment. Acceptance: correctly configured, independently verified, provider-dependent work documented.

## 3. Unified identity architecture
Complete the relying-party client per the committed architecture (`packages/dot-sso-client/README.md`, briefs, reports): OIDC code flow + PKCE S256; state/nonce validation; strict redirect validation; ID-token signature and claim validation; secure token exchange; stable identity mapping; local sessions; secure logout/revocation; back-channel logout where required; tenant isolation; role/permission preservation; secure errors and audit logging. Dot.Central is the pilot: prove sign-in through InfoDot with correct permissions and tenant boundaries. Only then the remaining migrations. Central authentication never replaces platform authorisation. Acceptance: production-verified central sign-in and a migrated Dot.Central pilot.

## 4. Ecosystem security + SSO migration
Verify the actual deployed inventory first. Per applicable platform, complete BOTH together where practical, one coordinated deployment each: (A) security headers (CSP adapted per platform, HSTS, nosniff, Referrer-Policy, Permissions-Policy, clickjacking protection, secure cookies, cache-control for sensitive responses — never weakened merely to silence violations) and (B) SSO migration (existing users sign in; identities mapped; memberships, roles, entitlements, tenant boundaries intact; legacy login/registration removed or blocked; sessions secure; logout/revocation correct; platform functionality operational). Rollback procedures; verify each deployed result; no simultaneous mass migration without a proven process. Acceptance: every applicable platform verified on both.

## 5. Retire legacy authentication
Not prematurely. Inspect usage of /auth/ecosystem, legacy redeem APIs, legacy tokens, old login routes. Before removal: all platforms migrated; no production clients depend on legacy; logs/telemetry checked; replacements functioning; rollback prepared; integration changes communicated; then remove safely. Acceptance: no active production dependency on legacy mechanisms.

## 6. Landing page — R-10 (one of the most important remaining product tasks)
InfoDot is a collective business mentor and practical business-support ecosystem — not merely Q&A, a directory, or articles. It helps people start businesses, validate ideas, fix operational challenges, improve performance, find experienced people and practical solutions, and grow. The page must communicate this within the first few seconds. Core message: InfoDot helps people start, understand, manage and grow businesses by connecting practical business knowledge, experienced people, credible solutions and business tools in one ecosystem.
Required sections: 1 Hero (immediate value proposition; clear actions: start a business / find solutions / join the community). 2 How InfoDot works (ask → discover solutions → learn from experience → apply → track progress). 3 Business Solutions (showcase the credible researched library; specific guidance, not motivation). 4 Business community (entrepreneurs and experienced owners contribute and help). 5 Business profiles (professional identity, capabilities, discoverability). 6 Growth and progress (tracking through activity, knowledge, ecosystem usage — never implying performance measurement without data). 7 Ecosystem capabilities (products as a coherent support ecosystem, explained by value, not a name list). 8 Trust and credibility (genuine capabilities, verified sources, transparent policies, real achievements — no fabricated logos, testimonials, user counts, stories or statistics). 9 Final conversion.
Acceptance: clear messaging; professional design; mobile responsive; excellent performance; accessible; functional registration/sign-in; working CTAs; SEO-friendly structure; metadata and social previews; accurate descriptions; no placeholders; no fake proof. Built around actual functionality only.

## 7. First real users (the biggest strategic gap)
Stop treating a technically complete platform as a commercially validated product. (A) First-user onboarding: a new user can understand the offer, register securely, create a profile, associate a business, state stage/industry/challenges, discover relevant solutions, ask a first question, find relevant discussions and contributors, and know what to do next — useful, not overwhelming. (B) A genuine initial community: practical launch strategy; early-adopter groups (aspiring entrepreneurs, small business owners, operators, consultants, industry professionals, business-development practitioners); real relationships over vanity metrics. (C) Reasons to return: evaluate Q&A, Solutions, tried-it, mentions, reputation, seminars, profiles, contributions, progress tracking for genuine value; no gamification for its own sake. (D) Early-user feedback loop: what problem brought them, whether they found and applied a solution, what happened, what they could not find, what to improve; distinguish engagement from business outcomes. Acceptance: a real onboarding journey and measurable feedback process ready for launch.

## 8. Commercial model validation
Inspect pricing/subscriptions: what is free, what is paid, tier contents, enforcement of limits, upgrades/downgrades, payment failures, cancellations, entitlement sync, admin management. Do not charge for non-functioning features. Pricing understandable and appropriate; keep key value accessible to resource-constrained entrepreneurs.

## 9. One-person operational continuity
Treat single-operator dependence as a continuity risk. Review hosting/registrar access, repositories, deployment credentials, backup encryption keys, recovery procedures, DNS/email administration, payment-provider access, critical credentials, monitoring, runbooks. Prepare a secure continuity package enabling another authorised technical person to maintain or recover InfoDot. No secrets in ordinary documentation. Document critical systems, access dependencies, recovery and deployment procedures, escalation contacts, recovery priorities. Identify single points of failure with realistic mitigations.

## 10. Business success measurement
Engineering metrics are not proof of helping businesses. Framework: platform adoption (registered/active users, businesses, completed profiles, returning users, contributors); knowledge usefulness (questions asked/usefully answered, solutions viewed/saved/tried, verified implementations, problems resolved); business outcomes where voluntarily provided (problems addressed, solutions implemented, operational/cost/revenue/productivity improvements, businesses started, milestones); commercial (paid subscriptions, transactions, MRR, conversion, retention, seminar registrations/attendance); quality and trust (source verification, solution quality, feedback, misinformation reports, contribution quality, incidents). Dashboards from real application data; never infer business success from clicks; no fake baselines or artificial activity.

## 11. Execution discipline
Use Laravel Boost and repo conventions; inspect before changing. Do not rebuild working components, replace architecture, introduce mock data, mark complete on code written, disable security for tests, modify production data without procedure, or claim external actions without evidence. Per change: inspect → root cause → smallest production-grade solution → tests → CI → security review → deploy via pipeline → verify live → record evidence → rollback documented. Statuses: NOT STARTED / IN PROGRESS / BLOCKED — OWNER / BLOCKED — PROVIDER / IMPLEMENTED — NOT VERIFIED / VERIFIED — READY FOR DEPLOYMENT / DEPLOYED — LIVE VERIFIED / COMPLETE. Implementation ≠ deployment ≠ production verification.

## 12. Execution order
P0 domain renewal (never delayed by engineering). P1 restore drill; Dot.Billing + Paystack; DNS/email; OIDC relying-party client + Central pilot. P2 ecosystem SSO + headers; legacy retirement; landing page R-10. P3 onboarding/early users; commercial validation; continuity; measurement. Owner/provider actions run in parallel with engineering — identify them early.

## 13. Final deliverables
(A) Production readiness report (evidence-based). (B) Outstanding work register (task, owner, status, dependency, next action). (C) Operational verification evidence (domain, restore, Paystack, DNS/DNSSEC, SSO pilot, headers). (D) Ecosystem migration report. (E) Landing page completion with live verification. (F) First-user launch readiness. (G) Commercial readiness report. (H) Business impact measurement framework. (I) Remaining owner actions with exact steps, time, access.

## 14. The standard
A platform can be technically excellent and still fail as a business. The real achievement: someone turns an idea into a functioning business; a small business solves a costly problem; an entrepreneur gets a practical answer from experience; a business finds a supplier, partner or opportunity; an owner implements a solution and sees measurable improvement; a user returns because InfoDot helps decisions; a business pays because it receives measurable value. **Do not optimise InfoDot for impressive audits. Optimise it for real-world usefulness, trust, adoption and sustainable commercial value.** Start with the outstanding operational risks and exact owner actions, close the highest-priority blockers, then finish R-10 and prepare for the first real users. Do the work. Verify the results. Be honest about what remains. The next milestone is not a development milestone. **It is the first real business that InfoDot helps succeed.**
